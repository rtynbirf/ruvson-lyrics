# КАРАОКЕ МЕЧТЫ 2.0 — Архитектура

## 1. Общая картина

Статическое SPA без сборки и зависимостей. Ядро в `karaoke/`:

```
karaoke/
├── index.html   — каркас: шапка, шесть экранов-секций, тост, audio-элемент
├── style.css    — неоновая тема (палитра в :root)
├── songs.js     — данные: 5 песен ЧИСТОВИК (секции + строки)
├── engine.js    — звук: транспорт, синт-минус, шифтер, микрофон, пад, LRC
├── app.js       — экраны и логика: библиотека, сцена, счёт, синхро, пати,
│                  голос, профиль
├── lrc/         — базовые метки песен (генерятся scripts/build_lrc.js,
│                  сверяются CI)
├── manifest.webmanifest · icon.svg · sw.js — PWA-контур (кэш km2-v3.1)
```

Модули общаются через один неймспейс `window.KM` (engine) и локальное
состояние `state` (app). DOM — прямой, без фреймворков: экранов шесть,
каждый — функция `render*()`.

## 2. Поток данных

```
песня (songs.js) ──► flattenLines() ──► linesWithTimes() ──► экраны
                              ▲                    │
localStorage (km2:timings:*) ─┴────────────────────┘
                                   тайминги живут отдельно от текста

Transport (файл | синт) ──► time() ──► tick() (rAF):
    ├── подсветка/заливка/отсчёт/скролл строк
    ├── Mic.read() ──► canvas-полотно
    └── Take.feed(t, idx, pitch) ──► finalizeTake()
                                          ├── best:*  (localStorage)
                                          ├── ref:*   (эталон-контур)
                                          ├── corridor:* (копилка полшага)
                                          ├── vector:<id> (профиль попытки)
                                          └── party.results (зал славы)
```

Базовые метки: `karaoke/lrc/<id>.lrc` ──► tryRepoLrc() ──► timings:<id>
(если своей синхронизации ещё нет; пометка `base:'repo'`),
генератор/валидатор — `scripts/build_lrc.js` (`--check` в CI).

## 3. Транспорт

Единый интерфейс `play / pause / seek / time / duration / setSemitones`
над двумя источниками:

- **file** — `<audio>` + MediaElementSource → PitchShifter (worklet) →
  master. MediaElementSource создаётся один раз за жизнь страницы.
- **synth** — планировщик WebAudio (lookahead 0.15 с, таймер 40 мс):
  пад (3 треугольника, lowpass 1100), бас (синус, огибающая), клик
  (квадрат 1500/2100 Гц), снейр (буфер шума, bandpass 1800).
  Позиция считается от `ctx.currentTime` якоря старта.

Событие `km-transport` на `document` — сигнал UI-хипам (кнопка Играть,
чип пада).

## 4. Питч-шифтер (AudioWorklet)

Классическая схема «дрейфующих линий задержки»:

```
k = 1 − 2^(semitones/12)          # скорость дрейфа
da(t+1) = (da(t) + k) mod G       # линия A
db = (da + G/2) mod G             # линия B — компенсирует разрыв
out = A·winA(da) + B·winB(db)     # окна Ханна, зерно G = 2200
```

Чтение из кольцевого буфера (16384) с линейной интерполяцией. При
`|st| < 0.005` — байпас (сэмплы проходят без обработки). Параметр
`semitones` — k-rate, меняется на лету; для синт-минуса транспонирование
делается проще — умножением частот осцилляторов.

Ограничение схемы: артефакт «хоруса» на полифонии — плата за темпосохранение
в 30 строк кода. Продакшн-альтернатива (пре-рендер минуса в нужной
тональности) — в роадмапе, этап 2.

## 5. Детектор высоты

`autoCorrelate(buf, sampleRate)` — нормированная автокорреляция:

1. RMS-гейт (0.006) — тишина отсекается сразу.
2. Обрезка краёв окна по 20 % RMS.
3. Корреляция лагов до `min(N/2, 2205)` сэмпла.
4. Первый устойчивый пик после спада → параболическая интерполяция.
5. Диапазон доверия 65–1200 Гц; `conf` = величина пика (0..1).

Кадры берутся в rAF из AnalyserNode (fftSize 2048 ≈ 46 мс окно).

## 6. Счёт и эталон

`Take` накапливает по активной строке (окно `start−0.1 … end+0.25`):
`frames / voiced (conf ≥ порога режима) / semis[]`. На закрытии строки и
в `finalizeTake()` считается `lineScore` (формулы в ТЗ, §2 слой 3).
Октавная свёртка `octFold(d) = d − 12·round(d/12)` делает дельту медиан
устойчивой к октавным ошибкам детектора.

Эталон-контур `ref:<songId>`: `{ offset }` — транспозиция, при которой
писался эталон; при сравнении ожидание корректируется на
`(curOffset − ref.offset)` — можно петь в другой тональности, счёт
остаётся честным.

## 7. Схема хранения

См. ТЗ §5. Все ключи с префиксом `km2:`. Принцип: текст каноничен
(в songs.js), время и голос — личное (в localStorage), экспорт — файлы
LRC. Ничего не уходит в сеть: единственные сетевые обращения — нет таких.

## 8. Безопасность и приватность

- Микрофон: `getUserMedia` → AnalyserNode **без** подключения к
  destination (нет заводки) и без записи/передачи; буферы живут в JS.
- Требование secure context (https/localhost) для микрофона — браузерное,
  приложение информирует пользователя вместо падения.
- Секреты (токены GitHub и прочие) в репозиторий не попадают никогда;
  `.gitignore` закрывает `.env`, `upload/`, `tool-results/`.

## 9. Расширение

Добавить песню: `ЧИСТОВИК`-текст → секции в `songs.js` (id `nNN`) →
Синхро-тапы → (опц.) экспорт LRC. Больше ничего: UI, счёт, коридор
подхватят песню автоматически.

## 10. v3.0 — новые модули

```
engine.js:
  mixDest (MediaStreamDestination)  master → mixDest; голос → recGain → mixDest
  Recorder   MediaRecorder(mixDest.stream), webm/opus или mp4, чанки 500 мс
  TakesDB    IndexedDB km2/takes: put/list(songId)/get/del
  detectKey  mono → FFT(8192, hop 4096, Hann) → chroma(12) → KS-профили(24)
  playGliss  глиссандо для разогрева

app.js (блок «v3.0 — ЭМЕРДЖЕНТНОЕ»):
  buildPath/ drawTubes      траектория эталона + канвас трубок
  duetAssign/applyDuetColors/duetParts
  renderWorst               «что тренировать» + переход к строке
  refreshTakes/playTake/stopGuide/syncGuide
  parseLyrics/initAddSong/deleteUserSong
  renderHighlights          хайлайты вечера
  Warmup                    60-секундный сценарий
  initMediaSession/updateMediaMeta/updateMediaPosition
  autoKey/suggestKeyStart
```

Поток записи: `master → mixDest` несёт минус (файл после шифтера или синт),
`mic → recGain → mixDest` добавляет голос; recGain не подключён к
destination, поэтому заводка невозможна, а колонки слышат только минус.
Медиа-запись стартует вместе с транспортом при включённой записи и
останавливается в `finalizeTake` (даже для частичной попытки).

Обновление кэша: правь `CACHE` в sw.js (и версию в `?v=` ссылок) одним
коммитом — иначе клиенты останутся на старом ядре.

## 11. Этап 4 — прогресс как поле

```
app.js (блок «ЭТАП 4 — ПРОГРЕСС КАК ПОЛЕ»):
  renderProfile            статы (попыток/лучший/Δv/отвоёвано пт),
                           журнал попыток, сводка, стирание (armed)
  drawGrowth               кривая роста (канвас, DPR-aware)
  allSongsTable            сводка по всем песням (клик — открыть)
  tryRepoLrc               автозагрузка lrc/<id>.lrc при первом открытии
finalizeTake (добавка):
  vector:<songId>          запись полной попытки {t, mode, score, cor, cov}
  corridor.credit          копилка полшага → шаг при 1.0, провал сжигает
  corridorSteps:<songId>   счётчик отвоёванных полутонов (за всё время)
```

Метаданные попытки пишутся только для полных (покрытие ≥ 60 %).
Кредит коридора живёт в `corridor:<songId>` рядом со сдвигом;
нормализация в `corridorOf()` делает старые записи `{offset}`
совместимыми без миграции. Δv — среднее последних 5 полных попыток
минус среднее первых 5: рост вектора, а не вчерашний рекорд.
`sw.js` кэширует lrc-файлы (кэш `km2-v3.1`).
